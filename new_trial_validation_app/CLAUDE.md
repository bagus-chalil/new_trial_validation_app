This is the **new** Laravel app replacing the legacy PHP app at the repo root (`../`). See `../CLAUDE.md` and `../MIGRATION_PLAN.md` for the overall migration plan, phase checklist, and SSO bridge design — this file only covers commands/architecture local to this Laravel codebase.

## Commands

```bash
composer run dev      # php artisan serve + queue:listen + vite dev, all concurrently
composer run lint      # pint --parallel (auto-fix)
composer run lint:check   # pint --parallel --test (check only)
composer run types:check  # phpstan analyse (larastan)
composer run test      # config:clear + lint:check + types:check + php artisan test
composer run ci:check   # npm lint:check + npm format:check + npm types:check + test

php artisan test                                  # full Pest/PHPUnit suite
php artisan test --filter=TestName                # single test by name
php artisan test tests/Feature/DashboardTest.php   # single file

npm run dev          # vite dev server (frontend only, use alongside `php artisan serve` if not using composer run dev)
npm run build         # vite build (add build:ssr for SSR build)
npm run lint          # eslint --fix
npm run format         # prettier --write resources/
npm run types:check      # tsc --noEmit
```

Tests use **Pest** (`tests/Pest.php`), not raw PHPUnit syntax, even though `phpunit.xml` configures the runner.

## Architecture

Official `laravel/react-starter-kit` scaffold — **Inertia.js**, not a decoupled REST API + SPA. Pages are server-rendered React components returned via `Inertia::render()` from controllers in `app/Http/Controllers`; there is no client-side router fetching JSON from a separate API for these pages.

- `resources/js/pages/` — Inertia page components (one per route), grouped by feature (`auth/`, `settings/`).
- `resources/js/layouts/` — shared layout shells (`app/`, `auth/`, `settings/`).
- `resources/js/components/ui/` — shadcn/Radix UI primitives.
- `resources/js/routes/` and `resources/js/actions/` — **generated by Laravel Wayfinder** (`laravel/wayfinder` + `@laravel/vite-plugin-wayfinder`), giving typed TS helpers for Laravel routes/controller actions. Don't hand-edit these — they regenerate from PHP routes/controllers on build.
- `app/Actions/Fortify/` — Laravel Fortify handles auth actions (registration, password reset, etc.); `app/Providers/FortifyServiceProvider.php` wires it up.
- `routes/web.php` / `routes/settings.php` — current routes are all Fortify/starter-kit boilerplate (profile, security settings) — no trial-validation domain routes exist yet.
- `boost.json` / `.mcp.json` — Laravel Boost is configured, providing MCP tools for this Laravel app (schema/route/log introspection etc.) when available in this session.

### RBAC / authorization (ported from legacy `bootstrap.php`, 2026-08-24)

`app/Models/User.php` maps onto the **real** shared `users` table (`password_hash`, `role`, `department`, `is_active` — no `password`/`email_verified_at`/`remember_token`/`updated_at`), not the starter kit's default schema; the fresh-install migration branch (used by sqlite/tests) was changed to match this same shape so behavior is identical in every environment. It carries role/department helper methods (`isAdmin()`, `isStaff()`, `isReviewer()`, `reviewDepartmentsForUser()`, etc.) ported from `is_admin()`/`is_staff()`/`is_reviewer()`/`reviewer_department_codes()` in the legacy app.

`app/Models/Trial.php`, `TrialReview.php`, `TrialEditPermission.php`, `MasterOption.php` are minimal stubs mapping onto the shared `trials_header`/`trials_review`/`trial_edit_permissions`/`master_options` tables — just enough for the RBAC port below; Fase 1 (Masters) and Fase 3 (trial workflow) will flesh them out with real CRUD/relations.

`app/Policies/TrialPolicy.php` ports `can_view_trial()`/`can_edit()`/`can_approve_trial()` (`view`/`update`/`approve` abilities — auto-discovered by Laravel via the `Trial`/`TrialPolicy` naming convention, no manual registration needed). `Trial::scopeVisibleTo()` ports the row-level list-scoping query from `scoped_trials_parts()` — use it wherever a trials list needs to be restricted to what the current user may see. Simple admin-only checks that aren't tied to a model instance (`can_manage_master()` etc.) are registered as Gates in `AppServiceProvider::configureGates()` (`manage-settings`, `manage-master`, `manage-parameters`, `view-products-template`, `manage-templates`).

Two gotchas hit while building this, relevant to any future model-mutating controller code:
- `User`'s `#[Fillable(['name','email','role','department'])]` attribute deliberately excludes `password_hash`/`is_active`/`deleted_at`/`deleted_by`. Mass-assignment helpers (`updateOrCreate`, `Model::update([...])`) silently drop those fields with no error — set them via direct property assignment (`$user->password_hash = ...; $user->save();`) instead.
- `AppServiceProvider::configureDefaults()` rebinds the `Date` facade to `CarbonImmutable` app-wide, so the `now()` helper returns a `CarbonImmutable`. Assigning that to a property typed as `Carbon` (e.g. `deleted_at`) fails Larastan. Use `\Illuminate\Support\Carbon::now()` explicitly for those assignments.

Two dependency/tooling notes from this session, relevant to any future table-heavy page:
- Installed `@tanstack/react-table` — pinned to `^8`, **not** the `^9` that `npm install @tanstack/react-table` resolves to by default. v9 is a from-scratch rewrite that removes `useReactTable`/`getCoreRowModel` entirely in favor of a different `useTable`/`createCoreRowModel` API; installing it bare breaks the build with `MISSING_EXPORT` errors matching every mainstream tutorial/example (including shadcn's own data-table docs), which all target v8's stable API. Explicitly install `@tanstack/react-table@^8` for any future table work in this app.
- `useReactTable()` trips the React Compiler's `react-hooks/incompatible-library` ESLint rule (a warning, not an error — `npm run lint:check` still exits 0) because the library returns functions that can't be safely memoized. This is expected/known for this library, not a bug to fix; the Compiler just skips memoizing `TrialsTable`, which is fine since it isn't passed into other memoized components.

Filter selects (status, product type) use plain native `<select>` elements, not the shadcn `Select` component — every other Select usage in this codebase so far is inside an uncontrolled `<Form>` with a `defaultValue`, and Radix's `Select` reserves the empty string internally for "no selection," which conflicts with an "All statuses" / "All product types" option needing empty-string semantics for a controlled filter bar. Revisit if a shared controlled-Select filter pattern is needed elsewhere.

### Server-side PDF export (Browsershot) (2026-08-28)

Replaced every `window.print()` button across the 6 report pages (`reports/approved`, `rejected`, `trial-summary`, `department-review`, `audit-print-log`, and the per-trial `trials/report`) with a real server-generated PDF download — the user's stated reason for prioritizing this over Fase 4: "kalau di print pdf tampilannya jelek banget" (the browser print output looked bad, since none of these Inertia/React pages had ever had real print CSS — only a `print:hidden` utility hiding the app chrome).

**Architecture decision made this session, not previously settled:** rather than pointing Browsershot at the live authenticated Inertia page URL (which would need session-cookie forwarding into the headless Chrome subprocess, plus a real running HTTP server — awkward in tests/CI and fragile across dev-vs-prod base URLs), each report gets a small **plain Blade view** (`resources/views/pdf/*.blade.php`) rendered to an HTML string via `view(...)->render()`, then handed to Browsershot as `Browsershot::html($html)->pdf()` — no HTTP round-trip, no auth/cookie plumbing, works identically in tests. This is what the original 2026-08-26 decision actually meant by "reuse the same HTML/CSS as the print views" (legacy's own report views are exactly this shape — plain server-rendered PHP, not client-rendered React).

- `App\Services\Pdf\PdfRenderer` (interface) / `BrowsershotPdfRenderer` (real impl, bound in `AppServiceProvider::register()`) / `PdfService::fromView()` (renders a Blade view, hands the HTML to the renderer, wraps the bytes in an `application/pdf` response with `Content-Disposition: inline`, so the browser opens the PDF in a new tab rather than forcing a download prompt). The `PdfRenderer` interface exists solely so tests can swap in `Tests\Support\FakePdfRenderer` (bound globally in `TestCase::setUp()`) instead of shelling out to a real headless Chrome on every request — fast and deterministic, and doesn't require Chromium in CI.
- `resources/views/pdf/layout.blade.php` is a self-contained `<style>` block (no Tailwind, no external assets — Browsershot renders a bare HTML string with no base URL) porting the relevant pieces of legacy's `public/style.css` print block (`.report-info-grid`, `.attachment-grid-print`/page-break-avoid tiles, compact `mm`-scale table typography) into plain CSS class names (`.info-grid`, `.attachment-grid`, `.page-break`, etc.). `TrialReportController::pdf()` and each `ReportController::*Pdf()` method pass a `title` + the same data shape the Inertia page already uses; page size/margins are Browsershot options (`->format('A4')->margins(10,10,10,10)`), not CSS.
- **Attachment photos are embedded as base64 `data:` URIs**, not URLs — `TrialReportController::attachmentDataUri()` reads the file straight off the `legacy_uploads` disk and inlines it, since a relative or route-based `<img src>` would never resolve (Browsershot's headless Chrome never makes a real HTTP request back to this app; it only ever sees the HTML string it was handed). A missing file (see [[local_uploads_dir_incomplete]]) renders a "File tidak ditemukan" placeholder in the PDF instead of a broken image.

### Line Configuration Report: assigned-approver email, sequential lock, and Return-as-action (2026-09-16, same day)

Direct user request right after the modal/sign-off-box pass above, refined twice more in the same session as the user reviewed the live result (see the two follow-ups below) — this section describes the **final** design; an intermediate version (versioning triggered by a `return_prod` checkbox left inside the general edit form, sign-off state carried forward unconditionally, no lock at all until Return) was built and then explicitly superseded, so don't trust any earlier commit/description of this feature over this one.

**Final behavior**:
1. The maker (PROD reviewer/Admin) fills the form and **assigns a specific user** to Approved(PIE) and/or Checked(PROD) via a `Combobox` (any active user — there's no "PIE" department/role coded anywhere in this system's master data). Assigning either one **submits** the report and **locks it** for the maker (`TrialLineConfigurationReport::isSubmittedForApproval()`) — no further edits to content or reassigning approvers, by anyone except Admin, until it's Returned. This closes a real gap the user caught live: without this lock, a PROD reviewer could silently edit data out from under an in-flight approval.
2. The chain is **sequential, not parallel**: Checked(PROD) cannot be confirmed until Approved(PIE) is (`TrialLineConfigurationReport::currentApprovalStage()` returns `'approved_pie'` first, then `'checked_prod'`). Emails follow the same step-by-step rule — the Approved(PIE) assignee is emailed immediately at assignment, but the Checked(PROD) assignee's email is deliberately **deferred** until Approved(PIE) is actually confirmed (fired from `MarkTrialLineConfigurationReportSignOff`, not from the save action), so PROD never gets pinged before it's really their turn.
3. **Return is its own action**, not a form field — a small dialog (reusing the existing `ConfirmDialog` component, same pattern as the trial-level Approve/Reject dialogs) requiring a reason of **at least 10 words** (client-side live word counter + the authoritative server-side check in `ReturnLineConfigurationReportRequest`). It's available only to whichever stage is *currently active* (`TrialLineConfigurationReportPolicy::returnReport()` — the Approved(PIE) assignee while PIE's stage is active, the Checked(PROD) assignee once it's PROD's turn, or Admin at any point) — never to the trial's own reviewers/approvers just because they're active elsewhere on the trial, and never to a stage whose turn hasn't come up yet.
4. Returning immediately locks the current version *as it stood at the point of return* (capturing exactly what was rejected and why) and clones a fresh current version forward with the same **content** (header fields, Production Standard, Line Configuration) but every **sign-off field reset** (approvals, assignments, return state all cleared) — a full new review cycle. This reset is a deliberate, necessary correction from the earlier "carry forward" design: if assignments carried over, the new version would be immediately re-locked by rule #1 above with no chance for the maker to actually revise it.
5. Once unlocked again, the maker sees the previous version's return reason as a prominent `Alert` (both on the read-only preview and inside the edit modal) so they know what to fix.

**Schema**: migration `2026_09_16_000003_add_assignment_and_versioning_to_trial_line_configuration_reports_table` adds `approved_pie_user_id`/`checked_prod_user_id` (nullable, no FK — same no-FK convention as every other column here), `version` (default 1), `is_locked` (default false), `locked_at`, and widens the unique constraint from `unique(trial_id)` to `unique(trial_id, version)` plus a `(trial_id, is_locked)` index; migration `2026_09_16_000004_add_return_reason_to_trial_line_configuration_reports_table` adds `return_reason` (text). `Trial::lineConfigurationReport()` (the `HasOne` used everywhere) filters `where('is_locked', false)` so it always resolves to the one live "current" row; `Trial::lineConfigurationReportVersions()` (`HasMany`, `is_locked=true`, newest first) exposes the locked history.

**Backend pieces**: `SaveTrialLineConfigurationReportRequest::authorize()` adds the submitted-lock check (blocks non-Admin once `isSubmittedForApproval()`); its `rules()` no longer accepts `approved_pie`/`checked_prod`/`return_prod` at all, only the two `*_user_id` assignment fields. `SaveTrialLineConfigurationReport` is back to a plain upsert plus the step-by-step email logic described above — it never sets any sign-off field itself. `MarkTrialLineConfigurationReportSignOff` (`approvePie`/`checkProd` actions, called from `TrialLineConfigurationReportController::approvePie()`/`checkProd()`) stamps the **acting user's own** name/`Carbon::now()`. New `ReturnTrialLineConfigurationReport` action + `ReturnLineConfigurationReportRequest` + `TrialLineConfigurationReportController::returnReport()` (`trials.line-configuration.return`, `POST {trial}/line-configuration/return`) implement point 3-4 above. `App\Policies\TrialLineConfigurationReportPolicy` gained the ordering checks (`checkProd()` requires `approved_pie` already true) and the new `returnReport()` ability. `TrialPolicy::view()` still has its bypass (added earlier this session, unchanged) granting view access to whichever trial's current report has the viewer as either assigned user — needed since the assignee is very often not a PROD reviewer/Admin at all and would otherwise 403 on the very page they were emailed a link to.

**`TrialReportController::show()`** sends `lineConfigurationReportLocked` (drives the "Dalam Proses Approval" badge), `lineConfigurationReturnNote` (the immediately-preceding locked version's reason/by/at, when the current version resulted from a return), `canReturnLineConfigurationReport` (alongside the existing `canApprovePieLineConfigurationReport`/`canCheckProdLineConfigurationReport`), and `canEditLineConfigurationReport` itself now folds in the lock+Admin-override check rather than being a bare Gate result. `downloadVersion()` (unchanged route from the first pass) serves a locked historical version as a read-only PDF via the existing `PdfService`/Browsershot pipeline, now also showing `return_reason` in that PDF and in the "Riwayat Versi" list.

**Frontend** (`line-configuration-report-section.tsx`): the edit modal's Sign-off block is two `Combobox` assignee pickers (hidden-input-mirrored, same pattern as `trials/review.tsx`'s reviewer/approver pickers) — Return(PROD)'s old checkbox+name+date inputs are gone from this form entirely.
