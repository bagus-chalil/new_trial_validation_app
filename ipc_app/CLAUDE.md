# CLAUDE.md — ipc_app

This is **IPC** (In Process Control), a Laravel + Inertia.js (React) app scaffolded from `laravel/react-starter-kit` — the same pattern as `../new_trial_validation_app/`, but a **fully separate project**. It shares no code, no database, and no auth/session with `../new_trial_validation_app/` or the legacy app at the repo root; the only thing tying it to those apps is that all three run on the same machine, on the same MySQL instance (as separate databases), and are reachable from the shared `../portal/` chooser.

Its predecessor is a Microsoft Power Apps/Dataverse app (a production quality-inspection tool: Startup Check → Filling → Packing → Finished Good → Approval → Print), not a MySQL app. That means **there is no legacy schema to stay compatible with** — unlike `new_trial_validation_app/`, which must match `trial_validation_system`'s existing `users` table (`password_hash`, no `email_verified_at`, etc.), this app's migrations are stock Laravel, unmodified. Do not port `Schema::hasTable()` shared-DB-skip guards or custom `users` columns from `new_trial_validation_app/` here — they exist there for reasons that don't apply to this app's own, exclusively-owned database.

**Implementation notes from the schema pass (2026-09-02, superseded where the reconciliation above corrected something):**
- Two deliberate refinements beyond the original design text (documented here since CLAUDE.md is the source of truth): (1) `startup_inspections`' checklist parameters (bulk color/texture, bulk odor, appearance after filling, leakage test, functional test, primer/sekunder/tersier, attribute, appearance) were normalized into a new `startup_inspection_items` child table (`parameter_key`/`status`/`remark` per row) rather than ~20 flat columns, for consistency with how `finished_check_samples` already normalizes its AQL groups — the original design text didn't specify flat-vs-child for this one. **Reworked 2026-09-03, same day, after the user compared the shipped page directly against real legacy screenshots** (`FILLING CHECK` screen — DATE/FG_CODE/NAME_PRODUCT/BULK_CODE/NO_BATCH/TH_PROGESS/IPC_ID/LINE header, per-sample result column, AVERAGE_WEIGHT, SAVE / SAVE & END / CANCEL buttons) and found the initial port too thin. Five real gaps fixed:

1. **Repeatable save (TH_PROGESS).** The original port treated every save as final — wrong. Legacy's QC workflow revisits the same Filling Check over a shift (re-weighing samples hourly to track drift), saving many times before ever finalizing; `TH_PROGESS` is legacy's own counter of how many times the record has been saved. Added `filling_checks.save_count` (migration `2026_09_03_010000_add_repeatable_save_to_filling_checks_table.php`) and a `finalize` boolean the frontend now sends on every submit. `SaveFillingCheckRequest`'s rules key off it: `finalize=false` (the new "Simpan" button) makes every field `nullable` and skips the all-10-samples cross-check, so QC can save 1 sample now and 3 more next hour; `finalize=true` (the "Simpan & Selesaikan" button, same behavior as the old single-button flow) keeps the original all-required validation. `SaveFillingCheck` increments `save_count` on every save (draft or final), only sets `completed_at`/advances `current_stage` to `packing` when `finalize` is true, and recomputes `weight_result`/`average_weight` from whatever samples are present either way — draft saves now show live per-sample results and a running average, not just the final one. `FillingCheckController::update()` redirects a draft save back to the same edit page (so the just-computed numbers are visible immediately) and only redirects to the batch overview on finalize.
2. **Info header added**, mirroring legacy's screen-top block: Tanggal, FG Code, No. Batch, Bulk Code, Line, IPC ID (current user, or the saving user once persisted), TH Progress, Nama Produk — all read-only display, sourced from `batch`/`fillingCheck`/`auth.user`, no new backend fields needed beyond `save_count`.
3. **"Standard Weight & Volume" free-text input replaced with read-only Max Weight / Min Volume**, sourced live from the batch's already-completed Startup Check (`startup_checks.filling_range_max`/`filling_range_min`) instead of asking QC to retype data captured a stage earlier. The `standard_weight_and_volume` column was dropped from `filling_checks` in the same migration as `save_count` above — nothing computes or stores it anymore. **Field-mapping assumption, still not confirmed by the user:** `filling_range_max` → "Max Weight", `filling_range_min` → "Min Volume" — the column names are generic on `startup_checks` (no legacy export text ties them to weight-vs-volume specifically), so this pairing is inferred from context, not a source document. Revisit if the user corrects it.
4. **Line, and (added in a same-day follow-up round) Line Leader, no longer re-asked here.** Legacy's screen shows a Line dropdown and a Line Leader text field on the Filling Check form itself; this app already captures `master_line_id` once at batch creation and `line_leader_name` once on Startup Check (`startup_checks.line_leader_name`), so Filling Check now just displays both (Line in the info header, point 2; Line Leader as a read-only field next to Max Weight/Min Volume) rather than duplicating either. `filling_checks.line_leader_name` was dropped entirely (migration `2026_09_03_030000_drop_line_leader_name_from_filling_checks_table.php`) — same treatment as `standard_weight_and_volume`. Note `startup_checks.line_leader_name` itself is `nullable` in `SaveStartupCheckRequest` (not required), so this display can legitimately show "—" for a batch whose Startup Check left it blank.
5. **Color capture via a real live camera stream, not a file/gallery picker.** First built as a plain `<input type="file" accept="image/*" capture="environment">`, then explicitly rejected by the user in the same session ("kalau bisa jangan attachment file... karena kalau gambar takutnya di manipulasi" — worried a gallery-sourced file could be a pre-existing/edited image, not real-time evidence) — `capture` is only a hint on many browsers/OSes and doesn't actually block the Files/gallery option. Replaced with `resources/js/components/ipc/camera-capture-dialog.tsx` (`CameraCaptureDialog`, reusable — built generically, not Filling-Check-specific, for whichever stage needs a photo field next): opens `navigator.mediaDevices.getUserMedia({ video: { facingMode: 'environment' } })` in a `Dialog`, shows a live `<video>` preview, "Ambil Foto" draws the current frame to a `<canvas>` and shows it as a preview with "Ambil Ulang"/"Gunakan Foto", and only the confirmed canvas snapshot (as a `File`, `image/jpeg` quality 0.9) is ever POSTed — there is no code path that accepts an arbitrary pre-existing file. Falls back from `facingMode: 'environment'` to a plain `{ video: true }` request if the exact constraint isn't satisfiable (e.g. a desktop with no rear camera), and shows an explicit error (no silent fallback to a file picker) if camera access is denied or unavailable. Requires a secure context (HTTPS or localhost) for `getUserMedia` to work at all — fine for local dev (`php artisan serve` on localhost) but worth remembering once this is deployed. Upload endpoint (`POST /batches/{batch}/filling-check/color-photo`, `FillingCheckController::uploadColorPhoto`, `UploadFillingColorPhotoRequest` — image mimes only, 8MB cap) is unchanged from the first round — still the app's first real use of `ipc_attachments` (required `php artisan storage:link`, run this session), still replace-not-append on re-upload.
6. **Per-sample result now computed live client-side too, not only after a save — and the earlier "-1" sentinel is now understood, not just approximated.** Re-reading `ipc_app/app_legacy/extracted/Controls/625.json` directly (the real Power Apps export) confirmed the per-sample result label (`Label5.Text` etc.) is `(Value(weight_input) - FL_TB.AVERAGE_OF_EMPTY_BOTTLE_WEIGHT) / FL_TB.DENSITY` — i.e. exactly the formula this app already had server-side — evaluated **live/reactively** as the operator types, not just on save. The "-1" visible in the legacy screenshots isn't a fixed constant: Power Apps coerces a blank input to `Value("") = 0`, so with a blank weight box the formula reduces to `(0 - AVERAGE_OF_EMPTY_BOTTLE_WEIGHT) / DENSITY` — for that particular demo batch's Startup Check values (`AVERAGE_OF_EMPTY_BOTTLE_WEIGHT=1`, `DENSITY=1`), that happens to equal exactly -1. It is coincidental to that one batch's data, not a universal rule — a batch with different Startup Check values would show a different blank-state number. The frontend now recomputes this same formula client-side on every keystroke (`liveResult()` in `edit.tsx`, using `batch.startup_check.density`/`average_of_empty_bottle_weight` now passed through in the `edit()` response) so the operator sees the result update in real time exactly like legacy's reactive label, falling back to the last-persisted server value only when nothing's been typed yet this session.

`SaveFillingCheckRequest` now requires (when `finalize=true`) only `sample_bulk_odor_status`/`sample_leakage_test_status` (Conform/Not Conform), `remarks`, `decision` (Passed/Hold/Reject), and all 10 weight samples — both `standard_weight_and_volume` and `line_leader_name` are gone per points 3-4 above. `StickySaveBar` (shared component) gained an optional `secondaryLabel`/`onSecondaryClick` pair for the new two-button layout — additive, doesn't affect Startup/Packing Check's existing single-button usage.

7. **Revision history (`filling_check_revisions`/`filling_check_revision_samples`), added same day after a separate, distinct user concern:** since `filling_checks` is `updateOrCreate`d in place on every save (draft or final), the user pointed out that a later draft save would silently overwrite or blank an earlier save's remarks/decision/samples — data they explicitly want preserved for reporting on how QC's assessment evolved across TH_PROGESS revisions ("kalau mau save yang kedua ... data1 beserta remarknya gk hilang karena itu nanti buat report"). `SaveFillingCheck` now writes an **immutable** `FillingCheckRevision` row (+ its own `FillingCheckRevisionSample` rows) on every single save, snapshotting exactly what that save contained, keyed by `revision_no = save_count` at that moment — the `filling_checks` row itself still only ever holds the *current* state (used for the live edit form and stage-lock), but nothing from an earlier save is ever lost. Surfaced in the UI as a collapsed-by-default "Riwayat Simpan" `AccordionCard` listing every revision (timestamp, saving user, decision, remarks, average weight), newest first. Not yet wired into any Report/Print screen (neither exists yet for any IPC stage) — this only guarantees the underlying data survives; presenting it as an actual report is future work.

Two migrations from this round were rolled back and edited in place rather than getting their own follow-up migration (`2026_09_03_020000`/`_020001`) — safe only because they were created and rolled back within the same session before any real data existed in them; don't do this to a migration that's already shipped/been run against data anyone cares about.

Original source: `IPC Power apps legacy.pdf` (repo root) — a screen-by-screen export including a raw Dataverse field-list dump, used for the first design pass before poppler/screenshot access was available. **Superseded 2026-09-02** by a much better source: `ipc_app/app_legacy/` (untracked), a real Power Apps package export (`.msapp`, unzipped to `ipc_app/app_legacy/extracted/`) containing the actual SharePoint list schemas (`References/DataSources.json`) and all 21 real screen definitions (`Controls/*.json`) — exact column names, exact dropdown choice values, and exact `Navigate()` call graphs. Everything in this section is now grounded in that export, not guessed from PDF screenshots. That legacy schema is flat/denormalized in the way Power Apps solutions typically are (30 numbered sample columns per table, 76 flattened `QST*(AC/CD/MD/MND)` AQL columns on Finished Check, cross-stage status flags all living on the Start record) — **the design below is a normalized reinterpretation for this app's own Laravel schema, not a 1:1 port of that raw table list.**

**Real screen flow graph** (confirmed via literal `Navigate()` calls in the export — MAIN's own button captions confirm each entry point's label):

```
MAIN ["START UP"]      → Start_Check ⇄ BottleData (30-sample sub-screen)
                          Start_Check ⇄ Start_Inspection (separate OK/Partial-OK/Not-OK checklist sub-screen)
MAIN ["FILLING"]       → Filling_List → Filling_Check → Filling_List
MAIN ["PACKING"]       → Packing_List_Test → Packing_Check → Packing_List_Test
MAIN ["FINISHED GOOD"] → Finished_List → Finished_Check → Finished_List
MAIN ["APPROVAL"]      → gallery_TEST → {StartReport_Approval, FIllingPackingReport_Approval, FinishedReport_Approval} → gallery_TEST
MAIN ["PRINT"]         → gallery_printer → {StartReport_View, FIllingPackingReport_View, FinishedReport_View} → gallery_printer
```

Confirms the original PDF-based read of the workflow shape (Home → Start Up → Filling → Packing → Finished Good → Approval → Print, each stage list filtered on the *previous* stage's completion flag, Approval/Print each split into 3 granular per-stage actions) — no correction needed there. **New finding, not in the original design:** `StartupInspection` and the 30-sample bottle-weight entry are *sub-screens reached from inside Start_Check*, not separate MAIN-level stages — each saves independently (`Patch()` to its own table) without requiring `Start` to be saved first. **Also confirmed: no Master Line admin screen and no Recycle Bin screen exist anywhere in the real legacy app** — matches this app's own Non-goals, nothing to port there. **Three screens are dead code** (`Report_List`, `Approval_List`, `Packing_List` — all superseded by other screens, zero live inbound navigation) — don't spend time reconciling against them if the export is revisited later. Decision vocabulary is confirmed exactly as originally read: check-level decisions use Passed/Hold/Reject (Filling, Packing), the Finished-stage disposition uses Accepted/Accepted With Remarks/Rejected.

**The legacy `tube` SharePoint list (Parameter/Spesification/Result/Decision/Operator/LineLeader/Worker) is dead — confirmed never referenced by any screen or formula in the export.** It reads as an abandoned early prototype, superseded by the purpose-built Start/Filling/Packing/Finished/StartupInspection tables. No corresponding table exists in this app's schema, and none is needed.

**Confirmed product decisions for this app (differ from legacy on purpose):**
- New `master_products` table (fg_code, product_name, bulk_code, is_active) — form fields become dropdowns validated against this master, not free text like legacy.
- Stage-lock rule is kept as legacy has it: once a stage is marked complete (its `end_yn`-equivalent flips, or the next stage has started), the prior stage's data becomes read-only for everyone — no role-based override for now (legacy has none either; the source PDF has the user's own handwritten note confirming this: "Kalau Sudah Y, di finish check gk bisa ya").
- `ipc_id` (the inspector name field on every legacy form) becomes a real `user_id` FK to this app's own `users` table, auto-filled from the logged-in session — not a free-text name like legacy, which improves audit-trail accuracy.

**Proposed entities:**

Master data:
- `master_lines` — category, area, code, name (the Line dropdown: e.g. category "Packing", area "Make Up", code "MU 01", name "Make Up 01")
- `master_products` — fg_code, product_name, bulk_code, is_active (see decision above)
- `master_test_types` — name, category (Leakage/Functional/Attribute), is_active — normalized replacement for legacy's flat "Test startup" table (VACCUM/TORSI/SPRAY/... as boolean columns); this is config, not per-inspection data, driving which test buttons render on Startup Inspection

Core:
- `ipc_batches` — fg_code/product/bulk_code (via `master_products`), no_batch, line_id, created_by (user), current_stage, timestamps. Takes over the "parent record carries whole-batch status" role legacy put on its Start table.

## Database

Own database, `ipc_system`, on the same local MySQL instance (`127.0.0.1:3306`) as `trial_validation_system` — but a completely separate schema with zero shared tables.

One-time local setup:
```powershell
mysql -u root -e "CREATE DATABASE ipc_system CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
cd ipc_app
php artisan migrate
```

**`migrate:fresh` / `migrate:refresh` / `db:wipe` are safe to run here** — `ipc_system` is exclusively owned by this app, nothing else reads or writes it. This is the opposite situation from `new_trial_validation_app/`, where those same commands once wiped the *shared* `trial_validation_system` DB by accident (see that project's `CLAUDE.md` and the `shared_db_wiped_2026_08_24` memory) — that incident doesn't apply here, but the general habit of double-checking `.env`/`DB_DATABASE` before a destructive migration command is still good practice. Note for Claude Code sessions specifically: this environment's own auto-mode safety classifier blocks `migrate:fresh` regardless of the above (hit 2026-09-02) — use plain `php artisan migrate` + `php artisan db:seed` (non-destructive, seeders use `firstOrCreate`) for routine verification instead.

## Auth

Stock Fortify, stock `users` table (`id`, `name`, `email`, `email_verified_at`, `password`, `remember_token`, timestamps). Registration is enabled by default — there's no legacy user base to seed against. No SSO, no shared session with the other two apps in this repo; a user needing access to more than one app logs into each separately.
